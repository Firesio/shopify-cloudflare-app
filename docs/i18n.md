# Internationalisation guide

The contract is `.claude/rules/i18n.md`; this is how the pieces fit and how to extend them.

## Layout

```
app/i18n/locales/<code>/{common,public,admin,email}.json   one JSON per namespace
app/i18n/locales/<code>/language.json                      { "name": "Español", "script": "Latn", "direction": "ltr" }
app/i18n/catalogues.generated.ts                           GENERATED: codes, names, scripts, directions, namespaces,
                                                           Resources type, flat key unions, SHA-256 digests of the en strings
```

`npm run i18n:sync` writes the generated file; `npm run i18n:check` (also run by `npm run typecheck` and the pre-commit
gate when a locale file is staged) fails when it is stale or a folder is malformed (a missing namespace file, a bad
`language.json`, a folder name that is not a canonical tag).

## Add a language (4 steps)

1. Create `app/i18n/locales/<code>/` (canonical BCP-47: `fr`, `pt-BR`, `ar`).
2. Add `language.json` (the `script` must be the one `Intl.Locale(code).maximize()` gives: `Latn`, `Arab`, `Hans`...) and one JSON per namespace with the keys of `en`. Plural keys need every category
   `Intl.PluralRules` gives that language (`x_one`, `x_other`; Arabic also `x_zero`, `x_two`, `x_few`, `x_many`).
3. `npm run i18n:sync`.
4. `npm run verify`.

Nothing else is edited: the server resources (`import.meta.glob`), the browser loaders (one chunk per language and
namespace, so a visitor downloads only theirs), the language switcher and `<html lang dir>` all read the folders. A
test proves it with a temp folder. A literal list of codes, or `startsWith("es")`, outside `locales/` and the
generated file fails a guard test.

## How a language is chosen

- Embedded admin: Shopify's `?locale=` is authoritative (never add a switcher there).
- Public pages: `?locale`, `?lng`, the `locale` cookie, `Accept-Language`, then `en` (`app/i18n/i18n.server.ts`).
- Every value goes through `negotiate` (`app/lib/language/tag.ts`), which is **script-aware, not truncation**: the tag is
  canonicalised (`_` accepted), its lookup chain is built from CLDR `parentLocales` then truncation (`es-MX` -> `es-419`
  -> `es`; `pt-AO` -> `pt-PT` -> `pt`; `sr-Latn` stops, CLDR says it does not inherit from `sr`), a step in another
  script than the request is dropped, and a catalogue matches a step only when language, script and region agree after
  `Intl.Locale.maximize()` (`pt` matches `pt-BR`, `zh` matches `zh-CN`). So `zh-TW` is never answered with Simplified
  Chinese: with only `zh-CN` shipped it gets English until a `zh-TW` folder exists. `es-ES`, `es-419`, `ES-es` and
  `es_MX` all give `es`.
- The CLDR table is `app/lib/language/parent-locales.generated.ts`, written by `node scripts/cldr-parent-locales.mjs`
  (needs network, so it is not part of verify; it records its source URL and CLDR version). Re-run it when upgrading CLDR.

## Two audiences, two types

Two different people read two different languages, and the types keep them apart (`app/lib/language/roles.ts`):

- `MerchantLanguage`: the merchant's, from Shopify's `?locale` only (`getMerchantLanguage(request)`).
- `AudienceLanguage`: whoever reads what the app sends or shows to someone else (a customer, an email recipient, a
  public visitor), chosen from evidence about that reader.

Anything an audience reads depends on ONE contract, `AudienceText` (`app/i18n/audience.ts`): `language`, `direction`,
`t` / `fixedT(namespace)` (typed with the generated flat key unions, so a typo is a build error), and `content(refs)`
(the app's own stored text in the reader's language). It is built only by `audienceTextFor` in
`app/wiring/audience.server.ts`. Emails and the public pages' titles already use it; admin code may not import it, and
audience code may not read the request's language or import `i18nServer` (guard tests).

Pieces behind it, each with a do-nothing default that an app replaces in `defaultAudienceDeps()`:

| Piece | Default | An app adds |
|---|---|---|
| `TextLayer`s per language (`layersFor`) | the shipped catalogue | an overrides layer above it, a merchant-language layer |
| `TEXT_UNITS` (`app/i18n/text-units.ts`) | one entry per email and public page | its own units |
| `ShopLanguages` provider | shop primary unknown, so shipped languages and `en` | the shop's synced languages |
| `ContentLocalizer` | returns the original text | a table-backed translator of its own content |

A render asks for a UNIT (a piece a reader sees as one thing). The reader gets a language only if the whole unit exists
in it (`isUnitComplete`), else the default language, so a half-translated email is never sent. The translator
(`createTranslator`) is a fresh i18next instance per render over a new object holding only that unit's keys: nothing
shared is mutated, there is no fallback language inside it, nesting (`$t(...)`), unescaped values and empty strings are
switched off. Its values are not HTML-escaped because the renderers (React, React Email) already escape; with a string
renderer, pass `escapeValue` (the default) instead, or the output shows `O&#39;Brien`.

Shipped catalogues are complete for every unit (a test). The `en-XA` pseudo-locale (accented, 30% longer, bracketed;
`app/test/pseudo-locale.ts`, tests only) renders the support reply in `app/wiring/audience.server.test.ts` and fails on any visible
copy that is still plain English.

## Recipes for apps (none is built here)

**Per-customer text overrides.** Store only the merchant's DELTA from the shipped text: (shop, language, namespace, key,
text, `source_digest`). Add a `TextLayer` that reads them (per request, memoised) above the shipped layer in `layersFor`.
Validate every edit, AI draft and import with the one validator (`validateText`, `app/lib/language/text-validator.ts`): a
string is plain text plus `{{allowedName}}` from the unit's slot spec, and it rejects `{{-`, `$t(`, `{{x, format}}`,
unknown names, control characters, new URLs, too-long text and an outdated source. Plurals only through a structured
editor with one field per CLDR category of that language.

- *Outdated rule.* Store `sourceDigest(sourceText)` with each override (SHA-256 hex; `SOURCE_DIGESTS` in
  `catalogues.generated.ts` holds the digest of every shipped `en` string, so no query is needed). When the current
  digest differs the override is "outdated": still served in a shipped language and flagged in the editor, but for
  legally significant text (disclaimers, terms, consent copy) it is NOT served: the original is used and the page says so.
- *Release policy for merchant languages.* Strict whole-unit completeness applies to a unit's FIRST use in a merchant
  language (record `unit_ready(shop, language, unit)` when a save makes it complete). After that a key a release adds
  falls back per key (the content language's catalogue, else English) and the editor shows "New text to translate". The
  only mixing is therefore a brand-new key after a release, and the merchant's own untranslated content.

**Merchant-added languages / shopLocales sync (OFF here).** Shopify exposes the store's languages as `shopLocales`
(`locale`, `primary`, `published`), which needs the `read_locales` (or `read_markets_home`) scope, and signals changes with
the `locales/create`, `locales/update` and `locales/destroy` webhooks. This template requests the scope for nothing and
subscribes to none of the topics. To enable: look the scope and topics up in the Shopify docs, add them to both tomls,
sync into a `shop_languages` table (keep unpublished languages: `published` is a fact), treat the webhook payload as a
trigger and re-read `shopLocales`, and implement `ShopLanguages.forShop` from the table.

**Translating the app's own stored content.** A table keyed (shop, language, kind, ref id, field) with `source_digest`;
implement `ContentLocalizer.localize` over it (one query per render, original when missing). Every repository that deletes
a translatable record deletes its translations in the same batch, with a test per kind.

## Extension locale files (optional)

If `extensions/<name>/locales/` exists, `i18n:sync` also writes that extension's locale files
(`en.default.json`, `<code>.json`) from a namespace file `ext-<name>.json` in each language folder, so the strings
live in one place. A file over the platform limit (15 KB for a theme extension, about 29.6 KB pretty-printed for a UI
extension) fails the sync; nothing is silently dropped. With no `extensions/` folder (the template ships none) the
block does nothing. `ext-*` namespaces never reach a browser.
