# Internationalisation guide

The contract is `.claude/rules/i18n.md`; this is how the pieces fit and how to extend them.

## Layout

```
app/i18n/locales/<code>/{common,public,admin,email}.json   one JSON per namespace
app/i18n/locales/<code>/language.json                      { "name": "Español" }   (only the name)
app/i18n/locales/namespaces.json                           { "common": "browser", "email": "server", ... }
app/i18n/catalogues.generated.ts                           GENERATED: DEFAULT_LANGUAGE, LANGUAGE_CODES / LanguageCode,
                                                           LANGUAGES (name + script + direction, the last two from Intl),
                                                           NAMESPACE_KINDS, BROWSER_NAMESPACES, Resources type,
                                                           flat key unions, which keys are plural groups
app/i18n/browser-loaders.generated.ts                      GENERATED: one lazy import per language and BROWSER namespace
```

`npm run i18n:sync` writes the generated files; `npm run i18n:check` (also run by `npm run typecheck` and the pre-commit
gate when a locale file is staged) fails when they are stale or a folder is malformed. The sync parses EVERY JSON file of
EVERY language (invalid JSON, a BOM or a non-object root fails it) and checks the folder name: it must be exactly the
canonical tag (`Intl.Locale(name).baseName`: `pt-BR`, not `pt_br` or `PT-br`), not `und`, with no extension, and no two
folders may be the same language, script and region once maximised (`zh` and `zh-CN`, `en` and `en-US`).

The script and the direction are never written: they are generated from `Intl` (`maximize().script`,
`getTextInfo().direction`), so a folder cannot claim a script it is not written in, and `directionOf` reads the generated
table. Each namespace's kind is DECLARED in `namespaces.json` (`"server"` for mail and for `ext-*` extension files), not
guessed from its name; a server namespace has no browser loader, so it can never be emitted as a public asset.

## Add a language (4 steps)

1. Create `app/i18n/locales/<code>/` (canonical BCP-47: `fr`, `pt-BR`, `ar`).
2. Add `language.json` (`{ "name": "<the language in itself>" }`) and one JSON per namespace with the keys of `en`. Plural
   keys need every category `Intl.PluralRules` gives that language (`x_one`, `x_other`; Arabic also `x_zero`, `x_two`,
   `x_few`, `x_many`). A group is plural when its `x_other` exists.
3. `npm run i18n:sync`.
4. `npm run verify`.

Nothing else is edited: the server resources (`import.meta.glob`), the browser loaders, the language switcher and
`<html lang dir>` all read the folders. A test proves it with a temp folder. A literal list of codes, or
`startsWith("es")`, outside `locales/` and the generated files fails a guard test.

## How a language is chosen

There is ONE negotiator (`negotiate`, `app/lib/language/negotiate.ts`, server only) and ONE evidence function per kind of
reader (`app/i18n/i18n.server.ts`):

- **Visitors, customers and anyone who is not the merchant in the admin:** `requestEvidence(request)` = `?lng`, the
  `locale` cookie, then every `Accept-Language` entry ordered by its `q` weight (`parseAcceptLanguage`). The page's
  language (`getLanguage`) and the audience builder (`audienceTextForRequest`) both use it. **Shopify's `?locale=` is never
  part of it**: it is the language of the Shopify admin USER. A guard test pins this, including the indirection.
- **The merchant inside the admin (`/app/**`):** `?locale=` first (authoritative), then the same evidence.
  `getMerchantLanguage(request)` is `?locale=` alone (what a ticket stores). Never add a switcher there.
- Everything is parsed once at the edge into a `LanguageTag` (`languageTagSchema`: canonical, `_` accepted, `iw` is `he`)
  and a shipped language is a `LanguageCode` (the generated union); no function inside takes a raw string.

`negotiate(evidence, available, fallback)` is **script-aware, not truncation**, and always answers (`fallback` is one of
`available`). For one tag, in order: the lookup chain (exact region, then the CLDR parent from `parentLocales`, then
truncation: `es-MX` -> `es-419` -> `es`; `pt-AO` -> `pt-PT` -> `pt`; `sr-Latn` stops, CLDR says it does not inherit from
`sr`; a step in another script is dropped), then ANY shipped region of the same language and script, first by code
(`es-ES` with only `es-419` shipped, `fr-FR` with only `fr-CA`, `pt-BR` with only `pt-PT`). Another script is never served:
`zh-TW` with only `zh-CN` gets the next piece of evidence, then English. The first piece of evidence that matches wins.

Known limit: CLDR keeps Norwegian `no` and `nb` as two locales and `Intl` does not alias one to the other, so shipping only
`nb` does not serve `no`. Ship the tag your readers send (`no`), or both.

The CLDR table is `app/lib/language/parent-locales.generated.ts`, written by `node scripts/cldr-parent-locales.mjs`
(needs network, so it is not part of verify; it records its source URL and CLDR version). Negotiation is SERVER ONLY (a
guard test): the browser is told the language the server chose and never negotiates.

## What the browser downloads

The server inlines, in the page, the language and the text of exactly the namespaces the MATCHED routes declare in
`handle.i18n` (`routeNamespaces`; `EntryContext.routeModules` holds every route of the build, so the matches decide). The
browser hydrates from that with no request, so a failed chunk cannot leave a dead page, and a public page never carries
`admin`. English is not loaded "just in case": shipped catalogues are complete (a test), so there is no fallback language.
Only when the bootstrap is missing, or a client navigation needs a namespace it does not have, does the browser load
(lazily, with retries) the browser namespaces it is missing, for its own language only.

## Two audiences, two types

Two different people read two different languages, and the types keep them apart (`app/i18n/roles.ts`):

- `MerchantLanguage` = `{ role: "merchant", code }`: the merchant's, from Shopify's `?locale` only.
- `AudienceLanguage` = `{ role: "audience", code }`: whoever reads what the app sends or shows to someone else.

Both wrap the ONE language type, `LanguageCode` (a tagged object, so there is no cast, no always-true guard, no throw).
An audience language is a SHIPPED language: it is the folder that gives it a name, a script and a direction. An app that
wants audience languages without a folder widens that type and supplies their direction itself.

**Two builders, because there are two readers, and each TAKES the role of its reader** (`app/i18n/audience.ts`):
`audienceTextFor` (a customer or visitor: `AudienceLanguage` or evidence, the shop's customer languages and customer-facing
layers) and `merchantTextFor` (the merchant: a `MerchantLanguage`, the shipped catalogue alone, no shop). Passing one the
other's language is a type error (tested). The reply to the merchant who opened a ticket is read by the MERCHANT, so it
goes through the merchant builder in the language stored on the ticket (their admin language when they opened it, parsed at
the read edge); a shop's customer overrides can never change it. Staff mail is `fixed` to the default language by this
app's choice. Each event's entry in `app/emails/registry.server.ts` says which (`fixed` or `merchant`), and `buildEmail`
passes the shop where customer mail needs per-shop seams.

The language a merchant's SUBMISSION stores does not depend on `?locale=` being on that request (an in-app navigation can
drop it): the form posts the language it was drawn in (`useLanguage()`) and the server parses it exactly
(`submittedMerchantLanguage`). The root loader never revalidates, so `<html lang dir>` is fixed for the document.
The page's language and every audience text of one request share one evidence read (`requestMemo`).

Anything an audience reads depends on ONE contract, `AudienceText` (`app/i18n/audience.ts`): `language`, `direction`,
`fixedT(namespace)` (there is no default namespace) and `content(ref)` (one piece of the app's own stored text in the reader's language). It is built
only by `audienceTextFor` in `app/wiring/audience.server.ts`. Admin code may not import it, and audience code may not read
the request's language or import `i18n.server` (guard tests).

**The unit is the type.** A render asks for a UNIT (`TEXT_UNITS`, `app/i18n/text-units.ts`), a piece a reader sees as one
thing, and each unit lists typed keys (`{ namespace, key }`, checked against the generated key unions; a plural group says
`plural: true`, and only a plural group may). `audienceTextFor({ unit: "email.layout", ... })` returns an `AudienceText`
whose `fixedT` accepts exactly that unit's keys; a PLURAL key takes its count as the second argument and a plain key takes none, so a plural without a count does not compile: a key outside the unit does not compile, so it can never render as a
raw key. A text built for a bigger unit is accepted where fewer keys are needed (the email layout takes any email's text).

Pieces behind it, each with a do-nothing default that an app replaces in `defaultAudienceDeps()`:

| Piece | Default | An app adds |
|---|---|---|
| `TextLayer`s per language (`layersFor`) | the shipped catalogue | an overrides layer above it, a merchant-language layer |
| `TEXT_UNITS` | one entry per email and public page | its own units |
| `ShopLanguages` provider | shop primary unknown, so every shipped language | the shop's synced languages (as shipped `LanguageCode`s) |
| `ContentLocalizer` | returns the original text | a table-backed translator of its own content |

The language and the layers are chosen ONCE per render (`chooseLanguage`). The reader gets a language only if the whole unit
exists in it (`isUnitComplete`): "has text" is defined once, in `resolveText`, as a non-empty string, so an empty string is
missing; a plural group needs one string per category of that language (`Intl.PluralRules`). Else the default language is
used, so a half-translated email is never sent. The translator (`createTranslator`) is a fresh i18next instance per render
over a new FLAT object holding only that unit's strings (`keySeparator` and `nsSeparator` off, so `x` and `x.y` are two
plain keys and nothing is a path): nothing shared is mutated, there is no fallback language inside it, nesting (`$t(...)`),
unescaped values, formatters (`{{n, number}}`) and empty strings are switched off. Values go in i18next's `replace`, not next
to its options, and `count` is its own parameter. The shipped catalogues are built once, flattened once and deep-frozen.
Its values are not HTML-escaped because the renderers (React, React Email) already escape; with a string renderer, pass
`escapeValue` (the default) instead, or the output shows `O&#39;Brien`.

`{{appName}}` is a default variable (`base-options.ts`, from `app/identity.ts`) used by every instance; it is in no JSON file
and no key list. Shipped catalogues are complete for every unit (a test). To render a unit under a pseudo-locale without a
non-shipped language, put `pseudoLayer` (`app/test/pseudo-locale.ts`, tests only) in `layersFor` for a shipped language, as
`app/wiring/audience.server.test.ts` does for the support reply.

## Recipes for apps (none is built here)

**Per-customer text overrides.** Store only the merchant's DELTA from the shipped text: (shop, language, namespace, key,
text, `source_text`: the English text it was written against). Add a `TextLayer` that reads them (per request, memoised) above the shipped layer in `layersFor`.
Validate every edit, AI draft and import with the one validator (`validateText`, `app/lib/language/text-validator.ts`, a
deliberate EXTENSION POINT: the template stores no merchant text, so only its tests call it): a string is plain text plus
`{{allowedName}}` from the unit's slot spec, and it rejects `{{-`, `$t(`, `{{x, format}}`, unknown names, names that are
i18next option names (`lng`, `ns`, `context`...; `count` only in a plural form), control characters (`\p{Cc}`, `\p{Cf}`
except ZWJ and ZWNJ, `\p{Zl}`, `\p{Zp}`, lone surrogates), new links (with a scheme, `www.`, or a BARE domain such as
`evil.com/pay`; trailing punctuation is ignored, so `https://shop.com.` is not new) and too-long text. Whether the text is
outdated is not its job (see below). Plurals only through a structured editor with one field per
CLDR category of that language.

- *Outdated rule.* Store the `source_text` each override was written against (the template keeps no digests: the editor
  needs the text to show what changed, and a comparison of two strings needs nothing else). An override is "outdated" when
  its stored `source_text` differs from the current shipped source: still served in a shipped language and flagged in the editor, but for
  legally significant text (disclaimers, terms, consent copy) it is NOT served: the original is used and the page says so.
- *Release policy for merchant languages.* Strict whole-unit completeness applies to a unit's FIRST use in a merchant
  language (record `unit_ready(shop, language, unit)` when a save makes it complete). After that a key a release adds
  falls back per key (the content language's catalogue, else English) and the editor shows "New text to translate". The
  only mixing is therefore a brand-new key after a release, and the merchant's own untranslated content.

**Merchant-added languages / shopLocales sync (OFF here).** Shopify exposes the store's languages as `shopLocales`
(`locale`, `primary`, `published`), which needs the `read_locales` (or `read_markets_home`) scope, and signals changes with
the `locales/create`, `locales/update` and `locales/destroy` webhooks. This template requests the scope for nothing and
subscribes to none of the topics. To enable: look the scope and topics up in the Shopify docs, add them to both tomls,
sync into a `shop_languages` table (keep unpublished languages: `published` is a fact), treat the webhook payload as a
trigger and re-read `shopLocales`, and implement `ShopLanguages.forShop` from the table.

**Translating the app's own stored content.** A table keyed (shop, language, kind, ref id, field) with the `source_text` it was written against;
implement `ContentLocalizer.localize` over it (one piece at a time, the original when missing; batch with a per-request memo inside it). Every repository that deletes
a translatable record deletes its translations in the same batch, with a test per kind.

## Extension locale files (optional)

If `extensions/<name>/locales/` exists, `i18n:sync` also writes that extension's locale files
(`en.default.json`, `<code>.json`) from a namespace file `ext-<name>.json` in each language folder, so the strings
live in one place. A file over the platform limit (15 KB for a theme extension, about 29.6 KB pretty-printed for a UI
extension) fails the sync; nothing is silently dropped. With no `extensions/` folder (the template ships none) the
block does nothing. `ext-*` namespaces never reach a browser.

## Known limits

- **A failed chunk is retried, but a browser may remember the failure.** The browser backend asks i18next to retry a failed
  `import()` (`callback(error, true)`). The imports are generated static specifiers, so a retry cannot add a cache-busting
  query, and a browser that caches a failed module fetch (the HTML module map) will fail the same way until a reload. That
  is why the primary protection is the inlined bootstrap, which needs no chunk at all; the lazy path only serves a missing
  bootstrap or a client navigation to a route with a namespace the document did not carry. Unverified per browser.
- A link inside merchant text is detected token by token (scheme, `www.`, a bare domain, a bare IPv4 address, fullwidth
  dots, joiners ignored). `Done.Thanks` (no space) reads as a domain and is refused; an IPv6 literal or a deliberately
  obfuscated address (`evil[.]com`) is not recognised. The validator is a gate for honest mistakes and a first filter, not
  the only control: a rendered email should still not make a merchant string clickable.
