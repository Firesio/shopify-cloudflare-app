# Shopify API invariants

**This file starts empty on purpose.** It is the project's memory, not a
reference — you fill it in as you learn.

A memo, not an authority. **The skill lookup always wins** — see
`@rules/shopify-and-ui.md`. What this file buys is two things:

1. Nobody re-derives a finding that already cost someone an afternoon.
2. Items that are still *unverified* stay labelled unverified, instead of
   hardening into folklore by repetition.

## Settled — do not re-litigate

Record a finding here only once it is confirmed against real docs or a real
store. Every row needs the design consequence, not just the fact — a fact
without its consequence gets re-argued.

|---|---|---|
| **Redaction tombstone (OUR DESIGN, not a Shopify rule).** Shopify's docs on `shop/redact` say to erase the store's data within 30 days and say **nothing** about reinstalls or tombstones. We keep `redacted_shops` (`shop_hash` = SHA-256 of the lower-cased domain, `redacted_at`; no domain, no Shopify id) so an erased shop is not recreated by Partner history, a late webhook or a sweep. A hash rather than the domain so the row does not identify the shop; it is the same function the logs use (`hashShop`), not an HMAC, because a rotated key would silently un-tombstone every shop. Written in the same D1 batch as the purge; cleared only by the merchant's own reinstall (`afterAuth` token exchange) | Reasoned from the docs' silence plus the observed gap (`applyRelationship` upserts a `shops` row for any shop in Partner events); covered by `app/routes/webhooks/redaction.test.ts` and `app/services/redaction.integration.test.ts` | Any new path that can create a shop row, event row or delivery row without the merchant acting must consult `RedactionGuard` (`app/services/redaction-guard.ts`). Webhooks for a tombstoned shop are still acknowledged with 2xx. A guard check and the write that follows are separate statements, so a purge committing between them can leave one stray row until the next purge; the page-level lookup keeps that window to one Partner page. **Unverified:** that Shopify never sends a legitimate non-redact webhook for a shop that reinstalled but has not yet authenticated (before `afterAuth` runs) |

Two that hold for every Shopify app, so they are here from the start:

| Finding | Design consequence |
|---|---|
| Webhooks deliver **at-least-once** | Every handler is idempotent — `@rules/design-patterns.md`. The replay test ships with the handler, not later |

## Webhook delivery, compliance and offline tokens (2026-10-08)

Verified against shopify.dev docs lookup on 2026-10-08. The first table is what the docs state; the second is what we
observed or inferred and is labelled as such.

| Finding (documented) | Source | Design consequence |
|---|---|---|
| A delivery succeeds only on a 2xx. **Any other status, including 3xx and 4xx, is a failure.** Shopify allows a 1 s connect timeout and 5 s for the whole request, retries up to **8 times over 4 hours**, and after 8 consecutive failures **deletes the subscription if it was created through the Admin API** (app-specific `shopify.app.toml` subscriptions are not removed, but that delivery is lost). | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries), [Troubleshoot](https://shopify.dev/docs/apps/build/webhooks/troubleshoot) | Entries acknowledge fast and hand off to a queue. A lost `app/uninstalled` or `shop/redact` is a compliance problem even when the subscription survives |
| HMAC is `base64(HMAC-SHA256(raw body, client secret))` in `X-Shopify-Hmac-SHA256`, compared in **constant time**, over the **raw** body. A length mismatch must not throw: in Node, `timingSafeEqual` on different-length buffers throws and surfaces as a 500. | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries), [Monitor orders](https://shopify.dev/docs/agents/get-started/monitor-orders) | `verifyShopifyWebhook` uses `crypto.subtle.verify` (constant time, returns `false` on any length) and answers 401, never 500 |
| If you rotate the app's client secret, **it can take up to an hour for the webhook HMAC to be generated with the new secret.** (The explicit "accept both secrets until one hour after revocation" rule exists only in the Shipping Partner Platform docs, [Authentication](https://shopify.dev/docs/beta/shipping-partner-platform/authentication); it is **not** stated for app webhooks.) | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) | `verifyShopifyWebhook` takes an **ordered list** of secrets (`webhookSecrets(env)`: `SHOPIFY_API_SECRET`, then the optional `SHOPIFY_API_SECRET_PREVIOUS`); a delivery is genuine if any non-empty entry signs it, each checked with `crypto.subtle.verify` (constant time), empty entries never match. Accepting the old secret is our inference from the documented delay, not a documented requirement. Set `SHOPIFY_API_SECRET_PREVIOUS` only for the rotation window and delete it afterwards (a revoked secret that stays accepted is a standing forgery risk). It does **not** cover the Shopify library's own session-token verification, which still takes one secret |
| Compliance webhooks (`customers/data_request`, `customers/redact`, `shop/redact`): answer **2xx** to confirm receipt, complete the action within **30 days**, and an **invalid HMAC must return 401**. `shop/redact` is sent **48 hours after uninstall**; `customers/redact` can be withheld up to six months. | [Privacy law compliance](https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance) | Never turn a 401 into a 200. `shop/redact` always arrives after the shop's tokens are dead, so a handler that needs a live session can never succeed |
| Expiring offline tokens last **60 minutes** with a 90-day refresh token. When no merchant session is active (webhooks, background jobs) the app refreshes server-side with the stored refresh token. **Refresh one store at a time**: two workers refreshing the same store concurrently can leave one holding a token the other already replaced. Persist each returned pair atomically. | [Offline tokens changelog](https://shopify.dev/changelog/posts/offline-access-tokens-now-support-expiry-and-refresh), [Access tokens](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), [More resilient refreshes](https://shopify.dev/changelog/posts/more-resilient-refreshes-for-expiring-offline-access-tokens) | Serialising refresh per shop is an **open gap** here: no lock exists in the Worker, and the library does not take one |
| A refresh that returns **401 `invalid_request`** is Shopify's single answer for every terminal case, **including a revoked or uninstalled app**. Treat it as **final**: stop retrying and re-authenticate on the next merchant visit. Network errors, timeouts, 5xx and 429 are transient and safe to retry. | [Authenticate without a template](https://shopify.dev/docs/apps/build/authentication-authorization/implement-token-exchange?lang=node) | A refresh failure for an uninstalled shop is an expected terminal state, not a server fault, and must never become a 500 |
| An expired or invalid ID token makes Shopify answer 400. The app should reply **401 with `X-Shopify-Retry-Invalid-Session-Request: 1`**; 5xx is reserved for failures a fresh token cannot fix. | [Authenticate without a template](https://shopify.dev/docs/apps/build/authentication-authorization/implement-token-exchange?lang=node) | Client-caused auth failures are 4xx. A malformed `host` is the same kind of caller error and answers 400 |
| Dedupe on `X-Shopify-Webhook-Id`; ordering is not guaranteed; delivery is not guaranteed, so run **reconciliation jobs** that re-fetch from the API. | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries), [About webhooks](https://shopify.dev/docs/apps/build/webhooks) | Idempotency guard on every consumer (already required). A missed `app/uninstalled` is recovered by reconciliation, not by hoping for the retry |
| **Ordering is not guaranteed, so a consumer orders by `X-Shopify-Triggered-At`, not by when it runs (2026-10-09).** Consequence found in this app: a queued or retried `app/uninstalled` arriving after a reinstall (`afterAuth` → `recordInstall`) used to mark an installed shop uninstalled and delete its sessions. | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) ("ordering is not guaranteed"); reproduced by `app/services/webhook-ordering.integration.test.ts` | `ConsumerDelivery.triggeredAt` carries `webhook_deliveries.triggered_at` (`parseTriggeredAt`: a missing/unparseable header falls back to receipt time, never NaN). `decideUninstall` (pure, `app/domain/webhook-ordering.ts`) applies the lifecycle's existing ordering key (`occurredAt`, then `externalId`) so an uninstall older than the current install is ignored; `ShopRepo.applyUninstall` repeats that key in its `WHERE`, so a reinstall racing the write still wins. `app/scopes_update` carries the complete scope set, so `decideScopesUpdate` drops a delivery older than the newest applied change (recorded at the trigger time, `shop_scope_changes.occurred_at`). Residual: `X-Shopify-Triggered-At` has one-second resolution and Shopify's clock is compared with ours (`recordInstall` stamps our `Date.now()`), so deliveries within about a second of an install are decided by the tie-break rather than by true order; equal-time scope updates apply in arrival order. The scope check reads then writes (not one statement), so two different scope deliveries processed at the same instant could still interleave |

|---|---|---|
| **`shopify.authenticate.webhook` (shopify-app-react-router) loads the offline session and, when it is within 5 minutes of expiry, refreshes it; any refresh failure becomes `throw new Response(undefined, { status: 500 })`.** The docs show this call as the way to verify a webhook and do not mention the refresh. | Read `authenticate/webhooks/authenticate.mjs`, `ensure-offline-token-is-not-expired.mjs` and `refresh-token.mjs` in the installed package; reproduced as a 500 in a test; production trace `kv_get → fetch → HTTP 500` for `app/uninstalled`, 2026-10-08 | Do not use `authenticate.webhook` where no Admin API session is needed. Use `verifyShopifyWebhook` (`app/adapters/shopify-webhook.server.ts`). It contradicts the docs' guidance to treat a terminal refresh 401 as final, so it is a library defect we route around, not a documented behaviour |
| The `host` query parameter is passed to `new URL("https://" + atob(host))` unguarded by `sanitizeHost`, so base64-valid garbage such as `9998966025409999999` throws and becomes a 500. | Read `shop-validator.mjs`; production 500 on 2026-10-08; unit test | `isSafeHostParameter` runs before the library and answers 400. This guard is ours; Shopify's docs do not specify host validation |
| **Decision (inference):** a validly signed delivery whose payload our parser rejects keeps a **non-2xx** answer. Retrying an identical payload cannot succeed, but Shopify retries 8 times over 4 hours, and during that window a too-strict schema can be fixed and redeployed so the retry lands. Acknowledging with 2xx would turn that into silent data loss, which is worst for compliance. The answer is made safe by keeping schemas lenient (require only the fields used) and by logging the rejection loudly. | Follows from "any non-2xx is a failure" and the 4-hour retry window | Compliance and scopes-update routes keep their 400. `verifyShopifyWebhook` answers 400 only for an envelope that cannot be attributed to a shop (bad domain, missing topic/id header, non-JSON body) |
| **Decision (inference, replaces the earlier "purge stays inside the request" decision, 2026-10-09):** the compliance webhooks are **verified, enqueued and acknowledged with 2xx** by `app/routes/webhooks/compliance.tsx` (the consumer writes the inbox row, see "Queue-first receiver" below); the work runs in the queue consumer as registry handlers (`shop/redact`, `customers/redact`, `customers/data_request` are `WebhookTopic`s, handler bridge `app/services/webhook-handlers/compliance.ts`). The docs give 5 s to answer but 30 days to complete the erasure, so a 2xx after the durable enqueue satisfies both, and a failed purge is retried by the queue (8 attempts, then dead letter) instead of being lost behind an already-sent 2xx. The consumer deletes its own delivery row as part of the purge, which is safe because `purgeTenant` now runs R2, then KV sessions, then the D1 batch **last** (the D1 batch is the commit point; any earlier failure leaves the delivery row so the queue retries). A redelivery after the purge finds no delivery row and is `missing` (acked, no effect); a fresh Shopify retry of the same webhook id after the purge is a new message whose admission finds the shop tombstoned, so it is dropped without a row (`missing`). Compliance topics are exempt from the consumer's "shop row is gone" guard (`topicRequiresShopRecord`), otherwise a `shop/redact` for a shop with no `shops` row would never run. `compliance.enqueued` logs the route's `durationMs` (what the 5 s limit constrains: verify plus one queue send) and `compliance.handled` logs the work's `durationMs` in the consumer | Docs: 5 s timeout, "process asynchronously", 30 days to complete (see the rows above) | The webhook body is **not retained** (the inbox keeps a hash), so the customer topics receive an empty payload; they only declare "no customer data stored". The day a customer column exists, carry the needed fields on the queue message's `intake` (as `app/scopes_update` carries `scopes`) and extend the handlers. Residual: Shopify's own retry of a delivery it considers failed can race the consumer; harmless because the purge is idempotent |
| **wrangler 4.125.0's `secrets` block has only `required`; there is no `optional` list**, and a missing required secret fails the deploy. So `SHOPIFY_API_SECRET_PREVIOUS` is deliberately NOT declared in `wrangler.jsonc`, and is absent from the generated `Env`. | Read `node_modules/wrangler/config-schema.json` (`secrets` → `required` only) and the deploy check in `wrangler-dist/cli.js` ("required secrets have not been set"), 2026-10-09 | The previous secret is read through `webhookSecrets(env)`, whose parameter type names it as an optional `unknown`. Set it with `wrangler secret put SHOPIFY_API_SECRET_PREVIOUS --env production` for the rotation window, delete it with `wrangler secret delete` afterwards. Revisit if a newer wrangler adds optional secrets |
| **The documented shape for compliance subscriptions** is `[[webhooks.subscriptions]]` with `compliance_topics` (array of `customers/redact`, `customers/data_request`, `shop/redact`) and a `uri`; the docs' example shows one subscription per topic, the configuration reference types `compliance_topics` as an array. The `[webhooks] api_version` is the version used to serialise payloads. The latest published example is `2026-10`; this repo pins `2026-07` in both tomls and in `app/shopify.server.ts` (`ApiVersion.July26`), which agree | [Webhooks get started](https://shopify.dev/docs/apps/build/webhooks/get-started), [App configuration](https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration), [Manage webhook subscriptions](https://shopify.dev/docs/apps/build/webhooks/subscribe), 2026-10-09 | Keep the single three-topic subscription (valid per the reference); do not invent keys. Moving to `2026-10` is a deliberate, single change across `shopify.app.toml`, `shopify.app.dev.toml` and `apiVersion` |
| **Open gap (partly mitigated, 2026-10-09):** refreshes are not serialised per shop **across the Shopify library and our code**. The library refreshes inside `authenticate.admin` / `unauthenticated.admin` and exposes no hook for a lock; a lock that covers it needs a per-shop coordinator (Durable Object, out of scope in `@rules/cloudflare.md`) or a lease around every call site of the library, which we do not control. KV has no compare-and-set either. **What IS protected:** our own uninstall probe (`app/services/probe-installed-shops.ts`) refreshes one shop at a time, holds a D1 lease per shop (`ShopTokenProbeRepo.acquireLease`, one conflict-guarded `INSERT … ON CONFLICT DO UPDATE … WHERE lease expired … RETURNING`, so two overlapping cron ticks can never both refresh the same shop), re-reads the stored session immediately before writing and never overwrites a pair that changed, and only touches sessions whose access token has already expired. **What is NOT protected:** a merchant request that makes the library refresh the same shop in the few milliseconds between our final read and our KV write; the worst case is the probe replacing a newer pair with one that is still valid, and Shopify's 2026-08-28 grace (the previously presented refresh token stays usable until its replacement is used) is the documented safety net | [Access tokens](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), [More resilient refreshes](https://shopify.dev/changelog/posts/more-resilient-refreshes-for-expiring-offline-access-tokens), [Authenticate without a template](https://shopify.dev/docs/apps/build/authentication-authorization/implement-token-exchange?lang=node) | Do not add a second refresher anywhere else. Anything that refreshes a shop outside the probe is unprotected by the lease |
| **Closed in code, unverified against a real store (2026-10-09):** a missed `app/uninstalled` is now detected by the `uninstall_reconciliation` cron sweep. Per tick it takes at most 50 installed shops (one query, least-recently-attempted first, 20 h cooldown after a success), and for each one, sequentially under a D1 lease, calls `POST https://{shop}/admin/oauth/access_token` (`grant_type=refresh_token`, form-encoded, per the docs) through `ShopifyTokenRefresh`. **200** stores the new pair; **401 `invalid_request`** with the stored pair unchanged since we presented it is **terminal** and goes through the same ordering-safe `recordUninstall` use case as the webhook, dated at the moment the probe STARTED (so a reinstall that lands during the call wins); **429, 5xx, timeout, network error** are transient (retried on a later tick, lease released, failure recorded); **any other status or a malformed body** is `unexpected` and never an uninstall (a 400 `invalid_client` from a rotated secret must not mass-uninstall the fleet). Shops whose access token is still fresh are skipped, and shops with no stored refreshable offline session are logged `no_session` and left alone | Read `refresh-token.mjs`; docs: terminal 401 `invalid_request` vs transient 5xx/429, and the same 401 is returned for "a token your app has already replaced" | The docs' 401 is ambiguous (unknown, replaced, expired, revoked and uninstalled all look alike), which is why the probe re-reads the stored session and treats a changed pair as `superseded`, not terminal. **Throughput:** production cron is daily (`30 3 * * *`), so 50 shops are probed per day; raise the cron frequency (or `PROBE_BATCH_SIZE`) before the fleet exceeds that. **Never observed against a real Shopify store**: the request shape and error handling follow the docs and are tested against a fake fetch only |

## Unknown-shop webhooks and uninstall-probe capacity (2026-10-09)

**Our design decisions** (Shopify's docs do not define either; labelled as ours, not documented behaviour):

| Decision | Reasoning | Where |
|---|---|---|
| **"Redacted" means TOMBSTONED, never "has no `shops` row".** A shop can legitimately have no row: a webhook can overtake the first embedded load that creates it. The consumer asks the tombstone table and the `shops` row separately (`shopStanding`) and `decideShopGate` decides. | The old `isRedactedShop` (= no row) silently dropped, and then DELETED the delivery row of, any webhook for a shop not yet recorded. | `app/domain/webhook-delivery-lifecycle.ts`, `app/services/webhook-consumer.ts` |
| Tombstoned shop, record-requiring topic: discard and delete the delivery row. Compliance topics always run, tombstone or not. | Nothing naming an erased shop may linger; compliance is owed an answer regardless. | same |
| **`app/uninstalled` for an unknown shop: run**, a logged no-op. The handler's `decideUninstall` returns `ignore/unknown_shop`, the delivery is marked processed (row kept as the record) and `webhook.shop_unknown` is logged with the shop hash. | An uninstall of a never-recorded shop has nothing to undo, and a row created later is newer than the uninstall, so retrying could never change the outcome. | `topic table: onUnknownShop: "run"` |
| **`app/scopes_update` for an unknown shop: defer** with a queue retry delay (60 s doubling to 3600 s cap, ~3 h across the retries), delivery row left as it is (`received`). On the final attempt it runs instead (no-op, `webhook.shop_unknown`, processed) so it settles rather than dead-lettering unrecorded. | The payload is the complete scope set the row will want once it exists; dropping it loses a fact that can still be applied. A never-installed shop costs at most a bounded number of cheap retries. | `onUnknownShop: "defer"`, `deferralDelaySeconds` |

**Uninstall probe capacity.** Limits are from the Workers limits page (https://developers.cloudflare.com/workers/platform/limits/, read 2026-10-09):
subrequests per invocation Free 50 / Paid 10,000; to internal services (KV, D1, R2) Free 1,000 / Paid = configured limit
(default 10,000); 6 simultaneous open connections; Cron Triggers CPU Free 10 ms, Paid 30 s for intervals under 1 hour and
15 min for 1 hour or more; 15 min wall clock per invocation.

- Each probe is **one external fetch** (token endpoint) plus KV and D1 calls (lease acquire/release, session read/write). The internal count per probe was not measured; assume it stays far below `1,000 / 40`.
- `PROBE_BATCH_SIZE = 40` keeps the external fetches under the Free cap of 50 even on the daily tick that also runs Partner history. Probes are sequential (never over the 6-connection limit), each with a 10 s timeout, so a tick is bounded at ~400 s wall, inside 15 min.
- **Capacity = batch x ticks per day.** Production runs the probe hourly (`0 * * * *`, probe only) plus on the daily maintenance tick: 40 x 24 = **960 shops/day**. A shop is re-probed after a 20 h cooldown, so one cooldown window covers `40 x 20 = 800` shops. Above ~800 installed shops the backlog grows: `uninstall_probe.backlog {overdue, batch}` is logged (count only) and `cron.sweep` for `uninstall_reconciliation` reports `overdue`. Raise capacity by raising `PROBE_BATCH_SIZE` on the Paid plan (10,000 subrequests allows hundreds per tick) or adding ticks.
- The previous schedule (one daily tick of 50) covered 50 shops/day, so a fleet over ~50 was never covered within the cooldown.
- Named-env `triggers` are not inherited: `env.production.triggers.crons` re-declares both crons, and `scripts/check-placeholders.mjs` fails the deploy gate if the hourly one is missing. The dispatcher matches `controller.cron` against `UNINSTALL_PROBE_CRON` (`app/domain/cron-schedule.ts`); any other cron, including the local `*/5 * * * *`, runs everything.

## Queue-first receiver, side effects and dead letters (2026-10-16)

Looked up on 2026-10-16. Cloudflare pages were read directly; "implied" means the page suggests it without stating it.

| Finding (documented) | Source | Design consequence |
|---|---|---|
| Shopify has a **one-second connection timeout and a five-second timeout for the entire request**; any response outside 2xx, including 3xx, is an error; keep-alive should be on. Queuing is described as the pattern "for ensuring you respond within five seconds" | [Verify deliveries](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries) | The request does HMAC, header checks and one queue send, nothing else |
| Shopify says apps should not rely on webhooks alone ("delivery isn't always guaranteed"), recommends periodic reconciliation with `updated_at` filters, and states ordering is not guaranteed across or within topics (use `X-Shopify-Triggered-At` or `updated_at`) | [About webhooks](https://shopify.dev/docs/apps/build/webhooks) | Reconciliation exists for `app/uninstalled` (probe). A topic with no reconciliation (`shop/redact`) depends entirely on durable acknowledgement |
| Subscription `filter` suppresses a delivery whose payload does not match; an invalid field name or type mismatch still **creates the subscription but suppresses all deliveries** | [Filters](https://shopify.dev/docs/apps/build/webhooks/customize/filters) | When filters are used for high-volume topics, each one needs a test that a matching delivery still arrives |
| `ctx.waitUntil()` extends a Worker for **up to 30 s after the response**, shared across all calls in the request; promises unsettled after that are **cancelled**. Work that must finish should be awaited or sent to a Queue | [Context (ctx)](https://developers.cloudflare.com/workers/runtime-apis/context/) | `waitUntil` is never used to make an acknowledged delivery durable. Only decoration may ride it |
| Queues give **at-least-once** delivery ("in rare occasions, may be delivered more than once"); the docs advise a unique id per message used as a primary key or idempotency key | [Delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) | The webhook id is the inbox PK; admission is `INSERT … ON CONFLICT DO NOTHING`, so a duplicate message is harmless |
| Queue message size limit is **128 KB**; 5,000 messages/s per queue; retention up to 14 days (Free fixed at 24 h) | [Limits](https://developers.cloudflare.com/queues/platform/limits/) | The raw payload is not forwarded anyway. A topic with large bodies needs a claim check (R2) |
| `Message.attempts` **starts at 1** ("The number of times the consumer has attempted to process this message. Starts at 1") | [Queues JavaScript APIs](https://developers.cloudflare.com/queues/configuration/javascript-apis/) | `workers/app.ts` used to add 1 on top (the consumer saw 2..10), so `FINAL_QUEUE_ATTEMPT = 9` fired on the 8th of 9 deliveries and the last one was wasted. Fixed; `workers/app.queue.test.ts` drives the real wiring and was mutation-checked against the old `+ 1` |
| Each D1 database is **single-threaded** ("processes queries one at a time"); 10 GB per database, not increasable; writes per second are **not stated** | [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) | A row per delivery is fine for rare topics and not for order/product volumes (see `docs/webhooks.md`, topic classes) |

| Our design decision (not a Shopify or Cloudflare rule) | Reasoning | Where |
|---|---|---|
| **The receiver writes only a queue message; the consumer writes the inbox row (`admitWebhook`).** The old receiver claimed the row, set it `queued`, then sent. A worker killed between the last two steps left a `queued` row with no message, and Shopify's retry was then taken for a duplicate: the delivery was lost, with no sweep to find it. `catch` cannot see a killed isolate | One durable write has no in-between state: the message is on the queue or the send threw (5xx, Shopify retries) | `app/services/webhook-ingest.ts`, `webhook-admission.ts`, `app/routes/webhooks/enqueue.server.ts` |
| The message carries `intake` (topic, ids, `triggeredAt`, hash, typed `scopes`), never the payload | Payloads may hold personal data and queues retain messages for days | `app/ports/webhook-queue.ts` |
| Scope values are re-recorded on **every** admission pass | `webhook_scope_observations` is `ON CONFLICT DO NOTHING`; a pass that died after the claim must not leave a row with no values, which `app/scopes_update` would apply as "every scope revoked" | `admitWebhook` |
| A message with no `intake` (enqueued by the previous receiver) skips admission; the `queued` status stays claimable | Rolling over without losing in-flight work. Remove both once the queue has drained | `isQueuedWebhook`, `TRANSITIONS` |
| **A failed post-uninstall reconciliation is logged, not retried.** Retrying the whole delivery was tried: with no Partner credentials (the test env has none) every uninstall failed with `MISSING_CREDENTIALS`, 7 tests failed, and in production it would dead-letter uninstalls whose real work was done | The failure is not always transient; a retry must be reserved for failures a later attempt can fix. Catching up is the daily Partner-history sweep (**unverified** that it also covers the subscription refresh) | `recordUninstall`, `reconcile-after-uninstall.ts` |
| `recordUninstall` **announces before cleanup and reconciliation** | A retry that finds the shop already uninstalled returns before any announcement, so one placed after a throwing step could be lost forever. Safe to do early: the notifier never throws and its dedupe key is the occasion | `app/services/record-uninstall.ts` |
| A dead-lettered delivery **notifies staff** (`webhook_dead_letter`: email + push, on by default), once, only when the dead-letter write applied, keyed `webhook-dead-letter:<deliveryId>` | Nothing consumed the DLQ or alerted: a dead `shop/redact` or `app/uninstalled` sat unseen. The announcement is decoration and never changes what happens to the delivery | `app/services/announce-webhook-dead-letter.ts`, `webhook-consumer.ts` (`deadLetter`) |
| A delivery that **never gets a row** (admission fails on all 9 deliveries, e.g. D1 down) is not announced | There is no row to dead-letter and D1 may be the thing that is down. The `webhook.queue` `failed` error logs and the DLQ are the trace | **Residual gap**, `docs/webhooks.md` |

| Unverified | Why it matters |
|---|---|
| `max_retries: 8` means nine deliveries. Cloudflare's batching page says the default is "retry delivery three times", which implies N+1 but does not state it | `FINAL_QUEUE_ATTEMPT = 9` rests on it |
| That a resolved `queue.send` means the message is durable. The pages read do not say | The whole acknowledgement guarantee rests on it; it is the recommended hand-off for work that must not be lost |
| Shopify's maximum webhook payload size, and what `include_fields` does exactly (a forum post says top-level fields only, no metafields; ~195 days old) | Decides whether a claim check is ever needed for order/product topics |
| A new receiver running against an **old consumer** during a rollout acknowledges new messages as `missing` (inferred from the old code, not observed) | Avoid gradual deployments for the release that introduces the queue-first receiver |
| Latency of the request path on production | "Well under 5 s" is from the code path (HMAC plus one queue send), not measured |
