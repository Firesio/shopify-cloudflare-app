# Internationalisation

**Every string a MERCHANT or VISITOR can read is translated. No exceptions on
those two surfaces.**

A hardcoded English string is a defect, exactly like a hardcoded hex colour: it
cannot be localised, and it will be missed when a locale is added. This applies
to the public pages *and* the embedded Shopify admin — the admin is not "internal",
it is the merchant's UI, and Shopify localises the chrome around it.

**The internal staff console (`/internal/**`) is English-only in this template, as an app choice, not a rule of the
platform.** It is the team's own tooling, not a merchant surface, so translating it would double the cost of every
console change for an audience that does not exist. Its route files say so at the top; that comment is the decision.
An app whose staff work in several languages can translate it with the same namespaces and recipe (add a namespace
folder file, use `t()`); nothing in the i18n setup prevents it.

If a merchant-visible string ever needs to appear in the console (a message copied into an email, a label a merchant
will be quoted), it belongs in a translated namespace, not in the console's own copy.

Shopify's own guidance is the reason this rule exists rather than being a
preference: localised apps are surfaced more prominently in the App Store and
churn less in non-English markets.
https://shopify.dev/docs/apps/build/localize-your-app

## The setup

| Piece | Where |
|---|---|
| One folder per language, one JSON per namespace, plus `language.json` (endonym, direction) | `app/i18n/locales/<code>/` |
| Generated codes, endonyms, directions, namespaces, `Resources` type | `app/i18n/catalogues.generated.ts` (by `npm run i18n:sync`; never edit) |
| Locale narrowing, `negotiateLocale`, derived tables | `app/i18n/config.ts` |
| Tags, lookup chain, negotiation (pure, imports nothing from the app) | `app/lib/language/tag.ts` |
| Server resources (`import.meta.glob`) | `app/i18n/resources.ts` |
| i18next options: base (no resources, browser-safe) / server | `app/i18n/base-options.ts`, `app/i18n/options.ts` |
| Lazy per-language browser loaders | `app/i18n/client-loaders.ts`, `app/i18n/i18n.client.ts` |
| Locale detection | `app/i18n/i18n.server.ts` |
| `Intl` formatting helpers | `app/i18n/format.ts` |
| Key types | `app/i18n/i18next.d.ts` |

Stable product identity (`name`, contacts, legal metadata) is authored once in `app/identity.ts`. Words that need
translating (the tagline, the email sender disclosure) are ordinary keys in `common.json` / `email.json`; `appName` is
**injected** (never written in a JSON file) and is also a default interpolation variable, so `{{appName}}` works
anywhere. Resources are built into new objects; nothing mutates shared ones during requests.

**Namespaces are split by surface**: `common` (everywhere), `public` (landing,
pricing, legal, support), `admin` (embedded Shopify app), `email` (transactional
mail). `email` (and any `ext-*` namespace, which only feeds a Shopify extension's locale files) never reaches a
browser. Declare what a route needs with
`export const handle = { i18n: ["common", "admin"] }` — `entry.server` ships only
the declared namespaces, so the admin bundle never carries the marketing and
legal copy.

**Resources are bundled, not read at runtime** (`app/i18n/resources.ts`). workerd has no
filesystem, so `i18next-fs-backend` cannot work, and an HTTP backend would add a
round-trip to every cold render. The browser never imports that file: it loads only its own language (and the default
as fallback) through `client-loaders.ts`.

## Where the locale comes from

Highest priority first — this order is deliberate and tested:

1. **`?locale=` — Shopify's own parameter.** Apps rendered in the Shopify admin
   receive the merchant's chosen locale in the `locale` request parameter. Inside
   the embedded app it is **authoritative**: the merchant already picked a
   language in Shopify, and the app must match the admin around it.
2. `?lng=` — an explicit switch on the public pages.
3. The `locale` cookie — the visitor's remembered public choice.
4. `Accept-Language`.
5. `en`.

**Never add a language switcher to the embedded admin.** It would let the app
disagree with the Shopify admin it sits inside. The switcher is public-only.

**Shopify sends regional tags** (`es-ES`, `pt-BR`). Always narrow through
`negotiateLocale()` (the lookup chain `es-MX` -> `es`), which falls back to the base language — a strict equality check
silently serves English to a Spanish merchant.

## Writing translated code

- `useTranslation("<namespace>")` in components.
- **In a `loader`, use `i18nServer.getFixedT(request, ns)`.** `meta` and document
  titles are produced before React runs, so the hook is not available there —
  translate in the loader and pass the string through.
- Interpolate, never concatenate: `t("home.connectedTo", { shop })`, not
  `t("connected") + " " + shop`. Word order differs between languages.
- **Keys are semantic, not the English text**: `pricing.getStarted`, never
  `"Get started"`. The English copy will change.
- `t()` is typed against the `en` files, so a typo is a build error.

## Formatting is part of translation

Translating strings is not enough. `1/2/2026` is January 2nd in `en` and
February 1st in `es`; `1,5` is one-and-a-half in `es` and one thousand five
hundred in `en`.

**Never hand-format a date, number, currency, list, or relative time.** Use
`app/i18n/format.ts` — every helper is pure and takes the locale explicitly:

- `formatDate` / `formatDateTime` — never print a raw ISO string. **`timeZone` is a
  required argument with no default.** Left to the runtime, a Worker prints UTC
  and the visitor's browser prints their own zone, so the server HTML and the
  first client render disagree and React discards the server markup (hydration
  error #418). The embedded admin reads the shop's own zone with `useTimeZone()`
  (the app layout loader resolves it once from Shopify's `ianaTimezone`, stores
  it on `shops.time_zone`, and provides it through `TimeZoneProvider`; it falls
  back to `UTC`). The English-only staff console and fixed-calendar content such
  as the legal pages pass the `UTC` constant from `~/i18n/time-zone`. Call
  `useTimeZone()` inside a component, never inside a plain helper — pass the zone
  to the helper as a parameter. A zone from outside is validated with
  `toTimeZone()`.
- `formatNumber`
- `formatMoney(locale, minorUnits, currency)` — **integer minor units**, per
  `@rules/code-craft.md`. It derives the divisor from the currency, so JPY (0
  decimals) and KWD (3) are right without a special case.
- `formatList` — never `join(", ")`; `es` uses "y", `en` uses "and".
- `formatRelativeTime`

## Adding a language

1. Create `app/i18n/locales/<code>/` (canonical tag: `pt-BR`, `ar`).
2. Add `language.json` (`{ "name": "<the language in itself>", "direction": "ltr" | "rtl" }`) and one JSON file per
   namespace, with the same keys as `en`.
3. Run `npm run i18n:sync`.
4. Run `npm run verify`. The tests enforce **identical key sets, no empty strings, identical `{{interpolation}}`
   placeholders, the plural categories `Intl.PluralRules` gives that language, and a current generated file.**

No code file lists the codes: a locale-code list or `startsWith("es")` outside `locales/` and the generated file fails a
guard test. Full guide: `docs/i18n.md`.

`LOCALE_DIRECTION` (from each `language.json`) drives `<html dir>`. Use logical CSS properties
(`padding-inline`, `margin-block`) per `@rules/styling.md` so an RTL locale is a
one-line addition rather than a layout rewrite.

## Layout must survive translation

German and Spanish run **~30% longer** than English, and Japanese much shorter.
Never size a container to the English string, never truncate without a title, and
check the longest locale — the Polaris guidance on text expansion applies to the
public pages too.

## Red flags

- A quoted user-visible string in a `.tsx` file
- `t()` called with a template literal built from a variable, unless the key set
  is a closed union
- `new Date(...).toLocaleDateString()` with no explicit locale — it silently uses
  the *server's* locale, which on a Worker is not the merchant's
- `.toFixed(2)` on money, or dividing by `100`
- Strings concatenated with `+` around an interpolated value
- Adding a key to `en` and not to every other locale
